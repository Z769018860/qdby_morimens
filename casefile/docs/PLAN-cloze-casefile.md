# 方案：《忘却前夜死亡调查报告》——「文档 + 完形填空」推理

> 状态：方案文档（尚未实现）。依据：对 `drepo` 整包（Godot 4.6 导出的 `drepo.exe` + `drepo.pck`，共 321 个资源）的逐项拆解，以及本仓库现有的忘却前夜数据与代码。

## 0. 一句话
把“读一堆残缺的第一人称死亡记录 → 用名册 / 地图 / 广播 / 规则文档交叉验证 → 填写死亡报告（死因、凶器、加害人）”这套玩法，换成忘却前夜的世界观与数据，做成本仓库首页那个“开发中”的项目。**我们借鉴的是玩法结构，不搬运原作的文字、美术、音频和字体**（见 §10 风险）。

## 1. 原作拆解（只记录结构与数量）

### 1.1 内容规模
| 项 | 数量 / 事实 |
|---|---|
| 死亡记录 | 41 条（名册 40 人 + 1 个“不该存在的第 41 人”）；正文合计约 1.8 万汉字，平均约 440 字/条，极短 |
| 系统文档（`00-*`） | 12 份：使用指南、任务指示书、报告填写指南、参考分析、禁入区域、地图、定时广播、早晨点名、记录仪说明、诱导措施，以及通关后才开放的 2 份机密 |
| 匿名消息（`MSG`） | 7 条：前 5 条各给出若干条**残缺记录名**（含 `??`），第 6 条是元提示，第 7 条是真相自白 |
| 名册 | 每人：姓名、学号、性别、社团、**配发武器**（41 种）、备注 |
| 地图 | 5×5 坐标（A–E × 1–5），14 个命名地点；另有按小时推进的“禁入区域”封锁时间表 |
| 报告字段 | 死因 9 类 + 凶器 14 类（含“无”）+ 加害人（名册 / “其他”） |
| 语言 | 日语原文 + 简中 + 韩语，文本放在 `story/logs/*.txt`，UI 在 `.po` |
| 窗口 | 记录阅览、学生名册、地图、记事本、死亡报告、提示、参考资料（通关后追加“扣押资料·毕业相册”） |

### 1.2 核心机制（这是我们要复用的东西）
1. **记录名就是谜题**。格式 `死亡序-坐标-学号`（如“第 N 个死、在 C3、学号 34”）。玩家必须自己推出格式、再凭线索拼出一条没见过的记录名去“恢复”。
2. **残缺线索 + 图结构**。文档头部带 `@refs`（机器可读的引用边，共 85 条，出度最大 4，入度最大 4）；正文里引用对方时常常只给一部分（`13-??-34`），玩家要用名册、地图、广播补全 `??`。
3. **索引上的进度提示**。每条记录左侧显示 `[X]`＝未恢复的引用数；提到未读系统文档的记录名带虚线；读完正文末尾自动追加“检测到指向其他记忆的参考，未恢复 X 件”。**用提示数量而不是答案来引导**。
4. **信息三角**：正文（第一人称，有主观盲点）× 名册（配发武器、社团、性别）× 地图/广播/点名（死亡序、时间、坐标）。一条结论往往要三处各出一个事实才唯一。
5. **规则文档当评分标准**。`REPORT` 文档规定了归类的边角情形（无加害人的三类死亡、自杀不记“自杀”而记具体手法、“凶器”必须与名册配发武器同名否则记“无”）。完形填空的“正确答案”由这份规则唯一确定。
6. **三栏完形 + 全对才确认**。报告 = 死因 / 凶器 / 加害人（无加害人时后两栏为“无 / 其他”）。三栏全对才计入“核实率”；有错只显示“存在错误的报告”，不告诉错在哪。
7. **答案数据极薄**。`solutions.json` 每条只有 `cause / weapon / culprit / club / coord / dord / num / issued` 和少量 `flavor`（决定确认时那句话的模板）。**文案是模板 + 数据拼出来的**（`被{who}用{weapon}杀死，死因：{manner}`）。
8. **提示是脚本化的三级阶梯**：`restore`（下一条该恢复哪条：先指向消息 / 指令，再指向人物与地点，最后给记录名）→ `confirm`（先指引重读，再给“凶器是什么”，最后给整行答案）。提示文本在 `.po` 里按记录逐条手写，但**分支结构完全模板化**（`hint.gdc` 的 `restore/confirm/keys/refs/item/weapon/noweapon/nonmurder/unknown`）。
9. **叙事反转放在元层**。通关前 6 条匿名消息逐步松动“锁扣”，最后一条揭示发信人身份；“人数对不上不是故障”这类话是在**教玩家用统计量自查**（第 41 人）。

### 1.3 依赖图的形状（便于我们设计）
- 入口只有 4 个（任务书里列出的 3 条 + 消息给出的完整记录名），之后全靠 `??` 补全和互相指向前进。
- 没有孤岛：每条记录要么被别的记录/消息引用，要么被消息直接点名；有 2 条“无出边”的叶子（最早与最晚的死者）。
- 难度主要来自**需要的信息源数量**，而不是文本长度：简单题 1 个事实（正文直说），中等 2 个（正文 + 名册），难题 3–4 个（正文 + 另一条记录里的装备转手 + 广播死亡序 + 区域封锁表）。

## 3. 完形填空：三层设计

### 3.1 L1 记录名完形（找路）
`NN-XY-SS` 中任何一段缺失，用其他信息补出：
- `NN` 死亡序：用广播“已死 X 人 + 依次报姓氏”、早晨点名、别的记录里的“第几个倒下”；
- `XY` 坐标：用地点名 → 地图查表（并考虑封锁时间：谁死在“已封锁区域”）；
- `SS` 学号：用名册（人名 → 学号）。
输入框做格式校验与“ERROR 404 无对应记录”提示；不存在的记录名**不扣分**，但每次错误输入计入“试错数”（供评级）。

### 3.2 L2 报告完形（结论）
- 字段：**死因 / 致死手段 / 加害人**（下拉 + 搜索，名册头像辅助）。
- 死因类别（建议 9–10 类，每类绑定一个现有关键词图标，让“读文档”与“游戏内的状态系统”互相印证）：

| 本作死因 | 对应关键词 / 状态 | 是否有加害人 |
|---|---|---|
| 中毒致死 | 中毒 | 他杀 / 自行（记“中毒”而不是“自杀”）|
| 出血致死 | 出血 | 他杀 |
| 融蚀致死 | 融蚀（禁入区 / 最终收缩）| **无**（记“其他”）|
| 斩击 / 钝击 / 刺击 / 射击 / 勒杀 | 按装备类别 | 他杀 |
| 反击致死 | 反击 | 他杀（谁被谁反击要看记录）|
| 坠落致死 | — | 他杀（被推）/ 自行（跳）二选一 |
| 意外死亡 | — | **无**（自身过失）|

- 规则文档（`00-REPORT` 的本作等价物）把所有边角情形写成**可判定条文**，并与 §3.4 的校验器共用一份规则表，避免“文档与评分不一致”。
- 判定：三栏全对才“确认”；错了只提示“存在错误的报告”。核实率 = 已确认 / 总数。保存时附★标记。

### 3.3 L3 文档内完形（你说的“文档 + 完形填空”的直译版，建议作为本作新增）
原作的“填空”只发生在报告表单里。我们增加**正文内的损坏文本**：

- 记录里有被损坏的片段，用 `█` 或乱码块表示：`被██用██杀死`、`第█个倒下`、`在██的灯塔`。
- 玩家在**记事本**里直接对该段落“批注 / 填入推断”（类似原作的“标记段落备注”）。
- 填入的内容分三种判定：
  1. **实体型**（人名 / 地点 / 装备名）：自动补全 + 名册校验，提交报告时作为附证；
  2. **数值型**（序号 / 时刻 / 人数）：给出范围，用广播与封锁表可唯一算出；
  3. **规则型**（归类选项）：从规则条文里选一条。
- 正确填满一段 → 该段落“点亮”（变成金色），并减少该记录的“未解析片段”计数；**全部点亮后，该记录的报告自动预填一栏**（不是自动确认），以奖励认真读文。
- 设计目的：让“读文档”本身就有可见反馈，而不是只靠最后的下拉框。

### 3.4 校验器 = 内容质量的唯一保证
所有文案写完之后，由脚本从“事件账本”（§4）反推：
- **唯一可解**：对每条记录、每个字段，在“该记录允许使用的信息集合”（本条正文 + 允许引用的其他记录 + 名册 + 地图 + 广播）下，候选答案必须恰好 1 个；
- **无环无孤岛**：记录依赖图是 DAG（允许互相引用，但存在合法恢复顺序），从入口可达全部节点；
- **装备链一致**：同一件装备在任意时刻只在一个人手里；
- **时间线一致**：死亡序与时间戳单调、整点广播的“已死 X 人”与账本一致、封锁表与死亡位置不冲突；
- **文风一致**：名册里的性别 / 社团 / 称呼与正文代词一致。
这些检查沿用本仓库 `casefile/tests` 的做法（把“可解性”写成测试）。

## 4. 内容生产管线（最重要，决定能不能做出来）

1. **事件账本先行**（`ledger.yaml`，人写，是唯一真相）。每个死者一行：`dord`（死亡序）、`time`、`coord`、`victim`、`cause`、`weapon`、`culprit`、`witnesses[]`、`holds{item: holder}`（该时刻装备在谁手里）、`unseen[]`（谁在场但记录里没写到）。
2. **线索预算表**：为每条记录分配 3–5 条“线索单元”，并标注类型：
   `T1 正文直说 / T2 间接描写（只写后果）/ T3 需名册 / T4 需地图 / T5 需广播与死亡序 / T6 需另一条记录 / T7 需规则文档`。
   - 难度由“结论所需 T 的种类数”决定：简单 1、中等 2、难 3–4。
   - 全局配比建议：约 25% 简单、50% 中等、25% 难；每个 `culprit` 至少有一条“看起来像另一个人”的干扰线索（红鲱鱼），但干扰必须能被某个 T3–T6 证伪。
3. **写作**：每条 300–450 字第一人称，**只能使用账本里的事实**；叙述视角的盲点（看不见谁、听错了谁的名字）是推理的来源，要在账本里记为 `blindspot`。可用 LLM 起草，但必须通过 §3.4 的校验再人工润色；禁止模型“补充新事实”。
4. **`@refs` 与残缺记录名**：由脚本从账本里自动生成引用边，并按“难度”决定记录名遮挡哪一段（遮 `XY` 最简单，遮 `NN` 最难）。
5. **提示生成**：沿用原作的**模板化阶梯**，不逐条手写长文：
   - `restore.1` 重读 [来源文档]；`restore.2` 点出该记录里出现的人物与地点；`restore.3` 给记录名；
   - `confirm.1` 重读 [记录]；`confirm.2` 按字段给方向（“凶器是 X，去名册里查谁拿着它” / “这不是他杀，看规则 R3”）；`confirm.3` 给整行答案。
   - 每条记录只需要少量“特例句”，其余由账本字段 + 模板拼出。
6. **成稿检查清单**（CI 跑）：账本 lint → 依赖图 → 唯一可解求解 → 文本中出现的每个实体都在名册 / 地图里 → 每个 T 类型都真的被某条正文支撑。

**工作量估计**（单人，含校验器）：账本与校验器 4–6 天；名册 / 地图 / 规则文档 3 天；40 条记录首稿（LLM 辅助）+ 校验迭代 8–12 天；UI 8–10 天；提示与教学 3 天；打磨 / 测试 4 天。合计约 5–6 周。想先出 MVP，可以只做 **12 条记录 + 5×5 缩小版地图 + 12 人名册**，约 2 周。

## 5. 数据结构（草案）

```jsonc
// persons.json —— 名册
{ "id": "awk_xu", "slug": "xu", "num": 18, "role": "CHORUS", "realm": "CARO",
  "faction": "医疗队", "issued": "wheel_0034", "note": "…", "avatar": "img/awk/xu.webp" }

// items.json —— 配发装备（命轮 / 造物）
{ "id": "wheel_0034", "name": "…", "kind": "wheel", "weaponClass": "slash|pierce|blunt|shoot|poison|none" }

// places.json —— 地点与坐标
{ "A1": {"name":"悬崖","lockAt":"D2 16:00"}, "C3": {"name":"信号塔","lockAt":"D1 18:00"} }

// records.json —— 死亡记录（正文用轻量标记）
{ "key":"13-C3-34", "victim":"awk_x", "when":"D1 14:20", "refs":["10-D4-20"],
  "body":"……{{b:加粗}}……[[blank:b17|被██用██杀死]]……",   // blank 指向 blanks 表
  "mask":{"seg":"XY"} }                                     // 记录名在引用处遮挡哪一段

// blanks.json —— 文档内完形
{ "b17": {"type":"entity","answer":{"culprit":"awk_y","weapon":"item_9"},"needs":["roster","rec:10-D4-20"]} }

// solutions.json —— 评分（和原作一样极薄）
{ "13-C3-34": {"cause":"poison","weapon":"none","culprit":"awk_y","flavor":"poison"} }

// system.json —— 规则 / 广播 / 点名 / 地图说明（00-*）
{ "00-REPORT": {"title":"…","body":"…","rules":[{"id":"R3","when":"suicide","then":{"cause":"by_method","weapon":"none","culprit":"other"}}]} }
```
`rules[]` 同时驱动**文档渲染**和**评分器**，保证“文档怎么写，评分就怎么判”。

## 6. 界面与交互

### 6.1 形态
推荐**桌面窗口式**（接近原作的“档案终端”体验），输入栏沿用本仓库 `casefile` 的终端风格；窗口：
**记录阅览**（索引 + 正文 + 标记 / 批注）、**名册**（搜索、排序、头像、配发装备）、**地图**（5×5，点击地点显示封锁时刻与已知事件）、**记事本**、**死亡报告**（逐条填表、核实率）、**提示**、**参考资料**（通关后追加）、**设置**（CRT 滤镜、字号、音量）。
手机上改为**底部标签页**，窗口变成全屏页。

### 6.2 复用现有代码
- `casefile/js/engine.js` 的指令解析、`board`、`note`、存档与提示框架 → 抽出“案件无关”的核心，新增 `recover / roster / map / report` 指令作为键盘流入口；
- `casefile/tests` 的数据完整性 + 可解性测试 → 扩展为 §3.4 的校验器；
- 首页账号（localStorage 登录态）→ 同步核实率、用时作为成就；
- 挂机游戏的 WebAudio 合成器 → 终端键入声 / 确认声 / 报告盖章声（无需音频文件）。

### 6.3 反馈细节（直接抄原作里“好用”的那些，但用自己的实现）
索引左侧 `[X]` 徽标；正文末尾“检测到参考，未恢复 X 件”；虚线表示未读系统文档；记录名右上角显示死亡时刻（线索来源）；“放大显示”；排序（恢复顺序 / 名称 / 参考次数）；剪切 / 复制 / 粘贴的记事本。

## 7. 两条内容线

### 7.1 主线（手写）《第七档案局·第 N 期》
36–40 条记录 + 6–7 条匿名消息 + 12 份系统文档，节奏：教学 3 条 → 主干 20 条 → 反转 10 条 → 收束。结局取决于核实率（并提供“真相文档”解锁条件，如全部确认）。

### 7.2 程序化“每日一案”（利用现有战斗引擎）
挂机游戏的战斗引擎是**确定性**的事件流（谁在第几回合对谁造成多少伤害、状态何时施加、谁倒下），非常适合当“账本”：
- 每天用固定种子模拟若干场 **1v1 / 小队对决**（引擎目前只支持两方，所以“全员混战”要拆成一串对决，每个对决的败者对应一条死亡记录）；
- 自动生成**死亡报告**的答案（死因 = 致命一击的伤害类型 / 状态；致死手段 = 技能名；加害人 = 对方）；
- 记录正文用模板 + 少量变量拼成（战斗描写 + 一句主观感受），并按难度遮挡信息（例如不写技能名，只写它的状态后果，玩家要凭**该唤醒体的 7 个技能 + 状态规则**反推）；
- 和手写主线共用同一套 UI 和校验器，且天然保证**唯一可解**（答案来自引擎，不靠人写）。
- 这条线也直接回应首页占位文案里的“复盘一场翻车：逐条质询当时的队伍、命轮与造物选择”。

## 8. 难度、教学与评分
- **教学**：前 3 条记录（任务书直接给出名字）只需要 1–2 个事实；系统文档按需出现（读到“按 REPORT 规定记凶器”时才推荐去读 REPORT）。
- **难度开关**：标准（有索引徽标 + 提示）/ 硬核（无徽标、无提示、记录名全遮挡）。
- **评级**：核实率（主）× 试错数 × 提示数 × 用时；首次全确认给“★”；硬核全确认给“☆”。
- **成就**：全记录恢复、全报告确认、零提示、零试错、发现“余出的报告”（第 41 条）等。
- **防剧透**：通关前系统文档的“机密”类不出现；MSG 的措辞只给方向不给答案。

## 10. 风险与合规
- **原作版权**：`drepo` 的故事文本、人物、美术、音频、字体、代码均属原权利人（包内还带有 Steam 集成与多套字体的各自授权）。本方案只借鉴“玩法结构”，所有文字、人物、坐标 / 武器清单**重新创作**；不要把 `.pck` 解出的任何文件放进本仓库或发布到页面。若你持有原作授权，并希望直接复用其内容，请先确认授权范围，我们再另行规划“官方模组”形态。
- **IP 混用**：忘却前夜是第三方 IP，同人需标注“非官方”；避免对官方角色做过激的虚构。
- **逻辑漏洞**：推理游戏最怕“不唯一”。必须以 §3.4 的校验器为准，LLM 只能写文字，不能决定事实。
- **难度失衡**：靠线索预算表 + 内测的“提示使用率 / 卡点热力图”（记录每条记录的平均停留时间）迭代。
- **手机体验**：窗口系统在小屏要换成标签页；输入框使用原生补全。
